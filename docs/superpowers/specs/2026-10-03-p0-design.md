# homie P0 — Design Spec

Date: 2026-10-03 · Status: approved in brainstorming, pending written review
Revised: 2026-10-10 — mobile-first Next.js PWA; online-first P0 with an offline fallback.
Hackathon: [Amazon Developer Hackathon 2026](https://amazonappdev2026.devpost.com/) — Alexa+ track (+ AWS Builder mini challenge)

## 1. Goal

An Alexa+ add-on that **remembers things for the user** and uses that memory with **Google Calendar** and **Google Maps**,
plus a **mobile-first Next.js PWA** where the user sees and controls everything stored. The same application supports
desktop browsers; “dashboard” below refers to this application, not a separate desktop product.

Success = a demo where a teammate, on a real Alexa+ device *and* in the web simulator:

1. tells Alexa where an item is, then asks for it later and gets the right answer;
2. states food preferences, asks for a dinner suggestion, and gets preference-ranked places + directions;
3. asks Alexa to remind them of a deadline / food expiry and sees it in Google Calendar and the dashboard;
4. attaches a to-do to an upcoming event and hears it when asking "what do I have tomorrow?";
5. installs homie on a phone, signs in from the home-screen app, views/edits/deletes all of the above, uploads a photo,
   and deletes all their data;
6. sees a useful offline fallback when disconnected and can recover on reconnect without a false save confirmation.

### In scope (P0)

Memory MCP tools · Calendar tools · Maps tools · S3 media storage foundation · Cognito auth (Alexa account linking +
dashboard) · mobile-first PWA (memories, calendar, media, simulator, settings), installation and offline fallback
· Bedrock-backed Alexa simulator · rate limits ·
Terraform dev stack · EC2 deploy · CI.

### Out of scope (deliberately)

- Deal alerts (e.g. KFC promotions) — no public deals API; Alexa can't push proactively from our server.
- Room scanning / spatial item map from images (P1 reach goal; S3 media is its foundation).
- Device location — Alexa doesn't pass it to MCP; we use the user's saved home location.
- Proactive Alexa notifications — reminders surface via Google Calendar's own notifications.
- Vector/semantic search — keyword recall + Alexa+'s LLM is sufficient at per-user scale.
- Storing copies of Google Calendar events.
- Per-token KMS encryption of Google refresh tokens (DynamoDB encryption at rest is used).
- Offline memory reads after a cold launch, persisted private data caches, queued offline writes, background sync,
  and conflict resolution. P0 requires a connection for server actions.
- Web push notifications and native app-store packaging. Reminders continue to use Google Calendar notifications.
- Phone geolocation and native voice capture; the existing saved-home and Alexa interaction model remains P0.

## 2. External constraints (from Alexa+ MCP Toolkit docs)

Sources: [Quickstart](https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-quickstart.html),
[Authentication](https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-authentication.html),
[Account linking](https://developer.amazon.com/docs/alexaplus/add-ons/category-sdk-mcp-account-linking.html).

- MCP spec **2025-11-25**, **Streamable HTTP** transport (legacy SSE deprecated).
- **Round-trip latency < 500 ms** per query.
- **Auth is mandatory**, two tiers:
  - Tier 1 (service): `client_credentials`, scope `mcp:service`, metadata at `/.well-known/oauth-authorization-server`
    (`token_endpoint`, `grant_types_supported` incl. `client_credentials`, `scopes_supported`); token endpoint uses HTTP
    Basic client auth, validates the `resource` parameter against the MCP server URI, tokens ≤ 3600 s, no refresh tokens.
  - Tier 2 (user / account linking): OAuth 2.1 `authorization_code` + PKCE S256, user scopes `mcp:tools` (`mcp:resources`).
  - Unauthenticated requests → `401 Unauthorized` **without** a `WWW-Authenticate` header.
  - Not supported: Dynamic Client Registration, OpenID Connect.
- Tooling: `alexa-ai` CLI (`configure`, `new mcp`, `deploy`), `addon.json`, web simulator + device testing.
- Local dev reachable via a tunnel (e.g. `cloudflared`).

## 3. Architecture

```
 Echo / Alexa app ──Alexa+──▶ ┌──────────── server (FastAPI) ─────────────┐
   (account-linked)  Bearer   │ /mcp        MCP Streamable HTTP, stateless │──▶ Google Places / Routes (API key)
                     token    │ /.well-known/oauth-authorization-server    │──▶ Google Calendar (per-user OAuth)
 Mobile PWA (Next) ──────────▶│ /api/*      REST for dashboard + simulator │──▶ Bedrock (simulator only)
   Cognito login      JWT     └──────┬───────────────┬─────────────────────┘
                                     ▼               ▼
                              DynamoDB (1 table)   S3 (media, private)
                    Cognito user pool issues every token (Alexa link, dashboard, M2M)
```

- **One FastAPI app** hosts both the MCP endpoint and the dashboard REST API; both call the same services.
- **MCP:** official Python `mcp` SDK, stateless Streamable HTTP, mounted at `/mcp`. Tools verify the token, resolve the
  user `sub`, call a service, return. **No LLM calls inside tools** (latency budget).
- **Simulator:** `/api/simulator/chat` runs Claude on Bedrock (Converse API with tool use) as an **MCP client of our own
  `/mcp`**, forwarding the signed-in user's access token — identical path to real Alexa.
- **Google:** Calendar via per-user OAuth (scope `https://www.googleapis.com/auth/calendar.events`, offline access →
  refresh token stored in DynamoDB). Maps via a server-side API key (Places API (New) Text Search, Geocoding, Routes API).
  All Google HTTP calls use `httpx` (async) directly, not `google-api-python-client`.
- **Hosting:** one EC2 instance running the existing docker compose + **Caddy** for automatic HTTPS. All AWS resources in
  Terraform. Local Alexa testing via `cloudflared`.

### Server layout

```
server/app/
  main.py            app, CORS, routers, MCP mount
  config.py          settings (env)
  auth.py            Cognito JWT verification (JWKS cache), current-user dependency, scope checks
  ratelimit.py       per-sub in-memory limiter
  mcp_server.py      FastMCP instance + tool definitions (thin, call services)
  routes/            health, wellknown, me, memories, media, calendar, google, simulator
  services/          memory.py, profile.py, media.py, google_auth.py, calendar.py, maps.py, simulator.py, db.py
  models/            pydantic schemas (Memory, Profile, Media, CalendarEvent, Place, Directions, …)
```

## 4. Auth (Cognito)

One user pool, one resource server defining `mcp:tools` and `mcp:service`, three app clients:

| Client | Flow | Scopes | Used by |
|---|---|---|---|
| `alexa-link` | auth code + PKCE, confidential | `mcp:tools` | Alexa account linking |
| `alexa-service` | client_credentials | `mcp:service` | Alexa service-level auth |
| `dashboard` | auth code + PKCE, public | `openid profile` + `mcp:tools` | Next.js dashboard + simulator |

Server-side verification on every request: signature via Cognito JWKS (cached), `iss` = pool, `token_use=access`,
`client_id` ∈ our clients, `exp`, required scope. MCP `tools/call` requires `mcp:tools` (a user token); `mcp:service`
tokens may only call `initialize`, `ping` and `tools/list` (registration / health check — exact needs confirmed in the
Milestone 0 spike). Failures → `401` with no `WWW-Authenticate` header.

`/.well-known/oauth-authorization-server` is a static JSON document built from settings, pointing at Cognito's
`/oauth2/authorize` and `/oauth2/token` endpoints.

**Known risk → Milestone 0 spike:** Cognito prefixes custom scopes with the resource-server identifier
(`<id>/mcp:tools`) whereas Alexa docs show bare `mcp:tools`, and Alexa requires `resource`-parameter validation on the
`client_credentials` token call. The spike verifies both against Alexa's registration/health check.
**Fallback:** a thin FastAPI token endpoint for `client_credentials` only (issues our own short-lived signed JWT with
`mcp:service`); account linking stays on Cognito.

**Dashboard login:** browser-side Cognito Hosted UI + PKCE via `react-oidc-context`; API calls send
`Authorization: Bearer <access_token>`. No Next.js server sessions.

**Installed-app auth spike (foundation milestone):** verify this flow on real iOS and Android devices before building
the memory UI. Cover login initiated inside the installed app, callback completion with PKCE state intact, cold launch,
background/resume, expired tokens and logout. Use a stable HTTPS origin with registered callback/logout URLs. Do not
assume a browser login transfers into the installed app: WebKit documents that local storage is not copied on
installation ([WebKit login storage behavior](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/)). A fresh
sign-in after installation is acceptable; a callback stranded outside the app or repeated redirect loop is not.
Record supported OS/browser versions and results. If redirects fail, resolve the flow and amend the plan before
proceeding; do not add native wrappers or switch auth architectures without evidence from the spike.

Keep query data in memory, key it by authenticated `sub`, and clear it on sign-out/account changes. Session expiry
must offer a usable sign-in path; when a form is dirty, explain that reauthentication is needed before navigating away.
Never send tokens via URLs or service-worker messages to bridge browser/app contexts.

## 5. Data model

### DynamoDB — table `homie-{env}`, keys `pk` (S) / `sk` (S), on-demand billing

| pk | sk | attributes |
|---|---|---|
| `USER#{sub}` | `PROFILE` | `timezone` (IANA), `home {address, lat, lng}`, `travel_mode` (DRIVE/WALK/BICYCLE/TRANSIT) |
| `USER#{sub}` | `MEM#{id}` | `kind` (item_location/fact/preference/todo), `content`, `tags[]`, `event_id?`, `media_ids[]`, `created_at`, `updated_at` |
| `USER#{sub}` | `MEDIA#{id}` | `s3_key`, `content_type`, `size`, `caption`, `tags[]`, `memory_id?`, `training_consent` (bool, default false), `status` (pending/uploaded), `created_at` |
| `USER#{sub}` | `GOOGLE` | `refresh_token`, `scopes`, `connected_at` |

- `sub` = Cognito `sub` claim (same for Alexa-linked and dashboard tokens).
- IDs are **UUIDv7** (`uuid.uuid7()`, stdlib in Python 3.14) → `sk` order = creation order. **Server moves to Python 3.14.**
- Timestamps stored as UTC ISO-8601; converted with `PROFILE.timezone` at the edges.
- Free-form preferences are `preference` memories; structured settings live in `PROFILE`.
- Missing `PROFILE` → defaults: timezone from first dashboard visit (browser-detected), else `UTC`; no home; DRIVE.

### Not stored

Google Calendar events (read live; Homie-created events tagged in Google with
`extendedProperties.private.homie = "1"`), place search results (a liked place becomes a `preference` memory).

### S3 — bucket `homie-{env}-media`, private, SSE-S3, CORS for the dashboard origin

- Key: `users/{sub}/media/{media_id}.{ext}`.
- Upload: server issues presigned PUT (5 min expiry, fixed `Content-Type` and `Content-Length`); browser PUTs directly;
  client then calls `complete`, server `HEAD`s the object to confirm and flips `status` to `uploaded`.
- View: presigned GET (15 min). Allowed types: `image/jpeg|png|webp|heic`, `video/mp4|quicktime`.
  Size caps: images 50 MB, video 500 MB.
- Never-confirmed uploads: listings ignore `pending` items; `pending` items older than 1 hour are deleted (item + object
  if it exists) during the next `GET /api/media` for that user.
- `training_consent` is the only gate for any future fine-tuning dataset export.

### Pydantic response shapes (not stored)

`CalendarEvent {id, title, start, end, all_day, location?, html_link, created_by_homie, todos: Memory[]}`
`Place {name, address, rating?, price_level?, open_now?, maps_url, why?}`
`Directions {duration_minutes, distance_km, mode, steps_summary: str[] (≤5), maps_url}`

## 6. MCP tools

| Tool | Inputs | Returns | External calls |
|---|---|---|---|
| `remember` | `content`, `kind`, `tags?`, `event_id?` | saved Memory | DDB put |
| `recall` | `query`, `kind?` | ≤10 Memory, keyword-ranked, newest on ties | 1 Query |
| `forget` | `memory_id` | ok / not found message | DDB delete (conditional on owner key) |
| `create_reminder` | `title`, `when` (ISO datetime or date), `notes?`, `remind_minutes_before?` (default 60; all-day → 9:00 local day-of) | CalendarEvent | Google events.insert |
| `upcoming_events` | `days` (default 1, 1–14) | CalendarEvent[] with linked todos | Google events.list + 1 Query |
| `find_places` | `query`, `near?` (address text; default home) | ≤5 Place | Places Text Search (+ Geocoding if `near` given) |
| `get_directions` | `destination`, `mode?` (default profile travel_mode) | Directions | Routes computeRoutes |

- **Recall ranking:** lowercase tokenize query and memory `content`+`tags`, drop stopwords, score = matched-token count;
  ties → newest. Zero matches → return the 10 most recent memories of the requested `kind` (or all) so Alexa's LLM can still
  reason.
- **Place ranking:** load `preference` memories, extract keywords that co-occur with the query domain (simple keyword
  overlap), append the top ones to the text query, then re-rank results by overlap; `why` names the matched preference.
- **Tool descriptions** are written as prompts for Alexa+'s LLM (when to use, what to pass, e.g. `recall`: "Use when the
  user asks where something is or what they told you before").
- **Errors → speakable text, never exceptions:**
  - Google not connected / refresh token revoked (`invalid_grant`) → mark disconnected, return "Your Google account isn't
    connected. Open the homie dashboard to connect it."
  - External call timeout (**400 ms** per Google call) or 5xx → "Google didn't respond in time, please try again."
  - Google 429 → "I'm being rate limited by Google, try again in a minute." (no retry loop)
  - No home location for `find_places`/`get_directions` without `near` → "Set your home address in the homie dashboard."
  - Ambiguous `when` that can't be parsed → ask the user to restate the date.
  - Per-user rate limit exceeded → "You're going a bit fast, try again in a minute."

## 7. REST API (dashboard + simulator)

All require the dashboard Bearer token (`mcp:tools` scope) and scope every operation to the token's `sub`.

| Method & path | Purpose |
|---|---|
| `GET /health` | liveness (no auth) |
| `GET /.well-known/oauth-authorization-server` | AS metadata (no auth) |
| `GET / PUT /api/me/profile` | profile read/update (address → server geocodes) |
| `DELETE /api/me` | delete all user data: all `USER#{sub}` items + `users/{sub}/` S3 prefix + revoke Google token |
| `GET /api/memories?kind=&q=&limit=` · `POST` · `PATCH /{id}` · `DELETE /{id}` | memory CRUD |
| `POST /api/media` | create pending record + presigned PUT |
| `POST /api/media/{id}/complete` | confirm upload |
| `GET /api/media?limit=` · `PATCH /{id}` · `DELETE /{id}` | list (with presigned GETs), edit caption/tags/consent/memory link, delete (S3 + item) |
| `GET /api/calendar/events?days=` | live events + linked todos (max 14 days) |
| `GET /api/google/connect` → `GET /api/google/callback` · `DELETE /api/google` | OAuth connect (state param bound to `sub`, CSRF-safe), disconnect + revoke |
| `POST /api/simulator/chat` | `{messages}` → `{reply, tool_calls[]}` |

List endpoints take `limit` (default 50, max 200).

## 8. Rate limits

Per-`sub` sliding-window limiter, in-memory (`dev-note`: single instance; move to DynamoDB counters if scaled out).

| Scope | Limit |
|---|---|
| MCP tool calls | 60 / min |
| `/api/simulator/chat` | 10 / min **and** 200 / day |
| `POST /api/media` | 30 / min (+ size caps enforced by presigned `Content-Length`) |
| other `/api/*` | 120 / min |

Exceeded → HTTP 429 (REST) or speakable message (MCP).

## 9. Mobile-first PWA (client)

Next.js 16, shadcn/ui, TanStack Query, types generated from FastAPI `/openapi.json` via `openapi-typescript`,
`react-oidc-context` for login. Design phone flows first, then adapt to desktop. Mobile: bottom tabs for Memories,
Calendar, Media and Settings as those pages ship; Simulator is reached from Settings. Desktop may use a sidebar with
all destinations. Sign-out lives in Settings, not in the bottom tab bar. Plan 1 includes a minimal Settings page for
account, installation help and sign-out; profile and Google controls arrive in Plan 2.

| Page | Content |
|---|---|
| `/` | sign-in landing → redirects to `/memories` when signed in |
| `/memories` | filters by kind, search, add/edit in a mobile full-screen editor (desktop dialog), delete (confirm), attached media thumbnails |
| `/calendar` | next 14 days, "created by homie" badge, linked todos; connect-Google empty state |
| `/media` | grid, photo-library/file picker and optional camera capture; desktop drag-drop; upload progress/retry, caption, tags, training-consent default off, view, delete (confirm), attach to memory |
| `/simulator` | chat with Alexa, shows tool calls per turn |
| `/settings` | account/sign-out, install help, Simulator link when available; timezone (auto-detected), home address, travel mode, connect/disconnect Google, delete all my data (typed confirmation) |

Every data view has loading, empty, error and connectivity states. Support 375 px through desktop, ≥44 px touch targets,
visible focus, text zoom and accessible labels. Use dynamic viewport height and safe-area insets for headers, bottom
navigation and editors; content must not disappear behind the keyboard or home indicator. Editors scroll, keep Save
reachable, preserve text after request failures and confirm discarding unsaved changes. Uploads run in the foreground;
show interruption honestly and allow an explicit retry (restart upload with a fresh presigned URL when needed).

### Installation, offline fallback and updates

- Add `src/app/manifest.ts`: stable app `id`, name/short name, `start_url: "/"`, `scope: "/"`, `display: "standalone"`,
  theme/background colors, 192/512 icons and a maskable icon; include an Apple touch icon and matching viewport metadata.
  Retain browser zoom. See [Next.js PWA guidance](https://nextjs.org/docs/app/guides/progressive-web-apps); verify APIs
  against the installed Next.js 16 version before implementation.
- Serve over HTTPS. Provide feature-detected installation help, including iOS Add to Home Screen instructions; hide it
  in standalone mode. Do not assume one install prompt API works across browsers. Installation itself does not require
  offline synchronization.
- Add a small service worker solely for a generic offline document and its explicitly listed public supporting assets. Network-first
  top-level navigation falls back to this document on network failure; do not cache authenticated HTML/RSC, `/api/*`,
  `/mcp`, OAuth callbacks, tokens or presigned media URLs. Exclude auth/API routes from fallback interception too.
  Private REST responses use `Cache-Control: no-store`; the auth library's token store is separate from these caches.
- When an already-open page loses connectivity, show a connection message and retain only its current in-memory data,
  clearly marked as potentially stale. Disable writes while known offline; also handle network errors because an online
  indicator does not guarantee reachability. No persisted mutation queue, automatic write replay, or success toast
  until the server confirms. Revalidate reads on reconnect/resume. If a write outcome is uncertain, check server state
  before retrying to avoid duplicates. Offline cold launch shows the fallback, not cached personal data.
- App releases take effect on normal user-initiated refreshes; the worker does not cache or manage app releases.
  No update prompts, release detection, forced reloads or cross-tab update coordination in P0. In-memory drafts do not
  survive a manual refresh, so users must finish or discard work first. Keep the worker's default activation lifecycle,
  serve it with revalidation headers, and version/clean up only its app-owned offline-fallback caches when they change.
- Register the worker only in production builds so development hot reload is unaffected. Test PWA behavior with a
  production build on the HTTPS staging origin.

## 10. Infrastructure

Terraform (`infra/terraform`), one `env` variable (`dev`, later `prod`):
Cognito (pool, resource server, 3 clients, hosted UI domain), DynamoDB table, S3 bucket (+CORS, lifecycle), IAM role for
EC2 (scoped to the table, bucket, Bedrock InvokeModel), EC2 instance + security group (80/443), Elastic IP.
EC2 runs `docker compose -f docker-compose.yml -f docker-compose.prod.yml`; the prod override adds a `caddy` service
(automatic HTTPS) routing `/mcp`, `/api`, `/.well-known`, `/health` to the server and everything else to the client.
Server env is an `.env` placed on the instance (secrets never in git).

The base compose (local dev) keeps server + client only — no local AWS emulation; dev uses the shared `dev` stack.

**Bring HTTPS phone testing into foundation work:** use a stable named HTTPS tunnel to a local reverse proxy routing
`/api/*`, `/mcp`, `/.well-known/*` and `/health` to FastAPI, and other requests to Next.js. The tunnel terminates TLS;
production EC2/Caddy deployment remains Milestone 6. Staging and production browser API calls use same-origin paths,
not `http://localhost:8000` (which points at the phone on a phone). Add the exact staging origin to Cognito callback/
logout allowlists, server CORS and S3 CORS where applicable. Register the later Google OAuth callback for that origin.
Do not use changing tunnel URLs for installation/auth acceptance tests.

## 11. Testing & CI

- **Server (pytest):** `moto` for DynamoDB/S3; `respx` for Google HTTP; JWTs signed with a test RSA key against a fake
  JWKS. Required cases: auth (wrong scope, expired, wrong client, missing → 401 without `WWW-Authenticate`),
  **cross-user isolation** (user B cannot read/update/delete user A's memories or media via REST or MCP), each tool's happy
  path + its error messages, recall ranking, rate limiter, presigned upload flow, delete-all-data.
- MCP tools tested through the SDK's in-memory client session.
- **Latency script** (`server/scripts/latency.py`): calls each tool against a deployed `/mcp`, prints p50/p95, fails if
  p95 ≥ 500 ms.
- **Client:** `bun run lint`, `bun run typecheck` (`next typegen && tsc --noEmit`), `bun run build`.
- **Mobile/PWA acceptance:** real iOS Safari + home-screen app and Android Chrome + installed app on HTTPS staging;
  record OS/browser versions. Verify install icons/start URL, cold launch, Cognito return/logout/expiry, keyboard and
  safe areas, 375 px layout/text zoom, offline cold launch, interrupted requests, reconnect/resume, account switching
  without stale data, and loading a new production build on manual refresh after finishing/discarding a draft, with no
  deployment-triggered reload of open pages. Add Google OAuth return and
  camera/library upload interruption checks when those features land. Desktop Chrome/Safari remain regression targets.
- **CI:** GitHub Actions on PRs — server ruff + pytest, client lint + typecheck + build.
